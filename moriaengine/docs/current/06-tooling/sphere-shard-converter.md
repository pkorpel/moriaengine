# SphereShardConverter

A one-time, offline migration tool (`SphereShardConverter/`, namespace
`SteamEngine.Converter`) that converted the original Erebor shard's real Sphere content
into moriaengine's own `.def`/`.scp` format. Not part of the running server - it was run
once to produce the `scripts/converted/` tree, which is what the live engine actually
loads. See [Architecture overview](../01-overview/architecture-overview.md) for where
this fits among the other top-level projects.

## What it does

`ConverterMain` (`SphereShardConverter/Main.cs`) reads raw Sphere source files from a
`convert/` input folder and writes converted output into `scripts/converted/`
(`ConverterMain.convertToPath`). `ConvertedFile` (`ConvertedFile.cs`) represents one
output file - it strips Sphere's own `sphere_`/`sphere_d_` filename prefixes
(`GetNewFilename`) and writes a `//Automatically generated by SteamEngine's converter`
header before dumping each contained `ConvertedDef`.

The actual per-block conversion logic is split by content kind: `ConvertedItemDef`,
`ConvertedCharDef`, `ConvertedThingDef` (the shared base for both), `ConvertedTemplateDef`,
`ConvertedRegion` - each knows how to translate one Sphere block type's own field/trigger
syntax into this engine's equivalent `.def`/`.scp` shape. `ConvertedConstants` holds
cross-reference tables (defname remaps, known-unsupported-field lists) the per-kind
converters consult.

## Why its output needed real content fixes later, not just a conversion pass

The converter is a blunt instrument by necessity - it couldn't verify that a Sphere
value or reference it couldn't resolve (an unknown macro, a renamed defname, a field
this engine doesn't model yet) was actually *safe* to drop; it just drops what it can't
convert and moves on, sometimes silently. This produced several real, confirmed content
gaps discovered well after the conversion itself, documented across multiple gameplay-
system pages rather than here:

- [Races & nations](../04-gameplay-systems/races-and-nations.md) - 5 of 9 profession
  starting-equipment templates were missing items the converter couldn't resolve
  (Craftsman's entire tool kit, several weapons, a typo'd crossbow defname).
- [Professions](../04-gameplay-systems/professions.md) - a systematic
  `Cooking`/`Fishing` starting-value drop affecting every profession's `.def`.
- [Housing](../04-gameplay-systems/housing.md) - house deeds' original converted content
  referenced the target house via `RESOURCES` (crafting's consumption-list syntax), which
  doesn't fit what a deed actually needs - the converted content for this feature was
  entirely commented out, not usably converted.

**General lesson for working with `scripts/converted/` content**: a `//guessed by
Converter`-style comment, a value that doesn't match the original Sphere source when
checked, or content that's entirely commented out are all real signals the converter
couldn't do a faithful job for that specific piece - worth cross-checking against the
original pre-conversion Sphere source (not just the wiki or this engine's own converted
copy) before trusting it, the same pattern that resolved several of the gaps above.

## Chardef field mapping (#555)

`ConvertedCharDef`'s own `LineImplTask` list used to cover almost nothing - `name`/
`category`/`subsection`/`description`/`anim`/`sound`/`mountid` only - so a fresh
conversion run silently commented out the vast majority of every chardef's real content
(#551 measured this at 1,422 fresh chardef blocks: `tevents` hit the fallback on 99.7% of
them, `armor`/`can` on 79.7%, `attack` on 75.6%, `icon` on 72.3%). #555 closed most of
that gap:

- **`icon`/`can`/`aggromode`/`combatspell`/`experience`/`tamingdifficulty`** - plain
  pass-through. `can`/`aggromode`/`combatspell`/`experience`/`tamingdifficulty` are
  NPCDef-only fields (confirmed live in `NPC.cs`/`AbstractCharacterDef.cs`) - emitting
  them on a PlayerDef (`c_man`/`c_woman`) would produce an "Invalid data" load warning, so
  `ConvertedCharDef` comments them out instead whenever `PrettyDefname` resolves to one of
  those two. `icon` is Character-level and always safe, PlayerDef included.
- **`attack`/`dam` -> `WeaponAttack`** - averaged via the same Sphere range/list-parsing
  logic `ConvertedItemDef.HandleArmorOrDam` already uses for weapon attack ranges
  (`Utility.SplitSphereString` + a plain arithmetic mean). NPCDef-only, same reasoning as
  above - commented out on a PlayerDef.
- **`ARMOR` -> `armorVsP`/`armorVsM`** - averaged the same way, then written to BOTH
  fields (not the old #44 hand-edit's tuple-split guess) - this is Character-level, safe
  on a PlayerDef too.
- **Skill teachers' `tag(ucimskill,x)` -> `TeachesSkill = <SkillName>`** (#828) - read from the chardef's `@userclick`,
  where Erebor sets it.
- **A `COLOR=` constant the archive never defines** (the teachers' `color_human`, `color_skin`, `COLOR_O_BLACKROCK`)
  is written commented out with a warning (#828): Sphere just gets 0, while here the def failed to parse every
  time it was instantiated. `ConvertedConstants` collects every `[DEFNAMES]` name in the first stage for this.
- **`[SPEECH x]` -> `[SpeechStub x]`** (#825, `ConvertedSpeech`) - the `ON=` patterns are kept and the
  Sphere script under them is written as comments. The engine's `SpeechStub` is a placeholder that a real
  speech of the same name replaces. See [NPC speech](../04-gameplay-systems/npc-speech.md).
- **TEVENTS (`event`/`events`/`tevent`/`tevents`/`speech`/`tspeech`/`triggergroup`/
  `triggergroups`)** - moved from `ConvertedCharDef` into the shared `ConvertedThingDef`
  (benefits itemdefs too) as a plain pass-through. The engine's own
  `AbstractDefTriggerGroupHolder.LoadScriptLine` already recognizes these field names
  directly (same mechanism wiring `e_banker` onto bankers, #509) - no renaming needed,
  unlike the converter's old dead `WriteAsTG` handler which incorrectly renamed the field
  to a nonexistent `"triggerGroup"` key. Every TEVENTS field is converted and assigned
  regardless of whether the referenced `[TRIGGERGROUP ...]` content exists - a missing
  group just logs a warning and no-ops rather than crashing - deliberate future-proofing
  (#551 decision #2) so implementing a hook later automatically "lights up" every monster
  already tagged with it.

**Loot (#791).** A chardef's `ON=@NPCRestock` `ITEM=` lines become `Loot = item[,amount]` lines
(`ConvertedCharDef.ConvertRestockLoot`), with the archive's `i_gold{700 999}` typo and glued-on
second `ITEM=` repaired - see [Monster loot](../04-gameplay-systems/monster-loot.md).
The rest of the block (#793): `ITEMNEWBIE=` -> `Equip =` (NPC gear, newbie), `COLOR=`/`NAME=` ->
`EquipColor =`/`EquipName =` for the latest gear line, `ADDSPELL=` -> `AddSpell =`. `tag(isBoss,1)`
in `@Create` -> `IsBoss = 1` (#794, bosses never turn [elite](../04-gameplay-systems/elite-monsters.md)).
A bow's `TDATA3` -> `AmmoType = "t_weapon_..."` (a coloured bow inherits its base's), and a jagged bolt's
`BleedCoefficient` from `nastaveni_arrowdamage_` 25 after its damage slot (#1070).
`spherename.scp`'s `[NAMES x]` -> `[NameList x]` with a `Name = "..."` line each (#1070), read by `NameList`
(`#NAMES_x` in an NPC's name, the thief's mask).
`tag(resist_silence,x)` -> `ResistSilence = x` (#1070, against Mind Blast's silence), ahead of the other `tag.resist_` lines.

**Regions (#813).** `spheremap.scp`'s `[AREA]`s become `[FlaggedRegion a_<name>]` sections in
`map.def` (`ConvertedRegion`): rects (Sphere's exclusive max made inclusive), spawn point, map
plane, flags (kept in Sphere hex), and a parent computed from which other region contains it.
`EVENTS`/`RESOURCES`/`RAINCHANCE`/`COLDCHANCE`/`GROUP` pass through as-is. `CLASS` is dropped.
`tag.nomask` -> `NoMask = 1` (no thief's mask there) and `tag.cFlags` (Sphere hex) -> `CustomFlags` in decimal:
`region_cf_denyRecall_in` 0x10, `_out` 0x20, `instantRes` 0x80 (#1070).
`tag.arena=1` adds the Arena bit (0x10000) to the area's `FLAGS` line (21 arenas; before #1116 it was dropped, so no arena counted
as one), and `tag.bf` -> `Battlefield` (the keep conquest's front: 1, 2 Gondor's keeps, -1, -2 Mordor's; Erebor's +-3 lines
are comments there and stay out).
Until #813 every area threw in the constructor (it wrote `createdat` as a `DateTime`, no longer
saveable), so no region was ever emitted. `sphereregion.scp`'s `[RegionType]`/`[RegionResource]`
are still commented out (region resources come next on #813).

**Verbatim trigger bodies (#670, #808).** Only `@Create` is normally consumed (into fields); a
few other trigger bodies are emitted as-is, keyed by defname in `ConvertedThingDef.passthroughTriggers`
- only after checking the body is simple enough for LScript (plain calls like `SAY("...")`, no
`if`/`endif`, no bareword `SAY text`). Currently `i_stone_raceclass`'s `@dclick` and 5 NPCs'
`@NPCRefuseItem` (`c_namestek_valky_g/_m`, `C_m_GUARD_ent1`, `C_f_GUARD_ent2`,
`c_ocs_guard_npc_killer`); the 4 bareword-SAY ones (kvest0001/0002, `c_strazce_knihovny`) are not.

**Collector bags (#1247).** A `TYPE=t_collector` item becomes a `CollectorDef` (`TYPE t_normal`), and its `@create`
settings (`tag.x=` or `tag("x",v)`) become def tags, see [collectors](../04-gameplay-systems/quests/collectors.md).

**Monster ability tuning (#653 onward).** `tag.*` lines in a chardef's `ON=@Create` that tune a
monster ability (`tag.npc_stun_chance`, `tag.explode_dmg`, `tag(e_lightnings_chance,100)`...)
become `NPCDef` override fields via the `ConvertedCharDef.abilityTuningFieldNames` table,
`{min max}` ranges kept, in the archive's own units. See
[Monster abilities](../04-gameplay-systems/monster-abilities.md).

**Applying a regen: whole files only.** `scripts/converted/` is never edited by hand - not even a
"surgical" insert of lines the converter generated. Copy every regenerated file whole over the
tracked one (the converter's upper-case names like `DRAGONS.def` map onto the tracked lower-case
paths). A fresh regen must diff to **zero** files against `scripts/converted/`; since #793 it does.
Files that used to show "unrelated drift" (DRAGONS/Golems/INSECTS/SPECIAL/UNDEADS, aldaron) were
simply stale vs converter features already merged - swapping them in added their missing
SelfresDelay/NpcCurse/Summoning/Sniper tuning.

**WEIGHT is written in stones (#889).** Sphere reads `3.0` and `.1` as tenths with the point ignored and an
undotted `10` as 10 stones; `nastaveni_armorweight` values are tenths.

**Random lists need commas (#763).** Sphere writes weighted random picks as
`COLOR={ colors_white 9 color_gray_lt 1 }`. LScript can't read that form when an identifier
comes first, because `name value` is an assignment there. The list collapses into one element,
and the def crashes the first time it's instantiated: `c_sheep_woolly` did, taking down every
test that spawned one. `ConvertedTemplateDef.FixRandomExpression` (comma-separates a `{...}`
list) was already applied to templates and constants. It now also covers `Color` and the
`model` taken from `ID=`. Equip `{...}` lists are parsed by `NPC.LoadScriptLine`, not LScript:
since #775 it understands Sphere's weighted pick (`Equip = {i_bardiche 1 i_halberd 1}`, spaces
or commas, weights optional) and rolls one item per spawn (`StartingEquipmentEntry.PickDefname`).

**Still genuinely unsupported** (need real new subsystems before a mapping would mean
anything, confirmed unchanged by this pass): `moverate`, `resources` (loot), `bloodcolor`,
`foodtype`, `desires`, `aversions`, `shelter`, `reslevel`.

## Runtime values from sphereworld.scp (#860)

Reading the definitions isn't enough: Erebor overwrote weapon, armor and ammo values at runtime
from the `nastaveni_*` variables in `save/sphereworld.scp`. `SphereWorldVars` loads that file's
`[VarNames]` from the `convert/` folder, and `ConvertedItemDef.ThirdStageFinished` applies the
values over what the definitions said (`ConvertedDef.Replace`). See
[combat.md](../04-gameplay-systems/combat.md#where-the-numbers-come-from-860) for the table.
Without the file the converter warns and keeps the definitions' values.

## Current status

Dormant between uses, but buildable - retargeted to SDK-style/net8.0 and added to
`SteamEngine.sln` (#543) so it no longer silently bit-rots the way the original legacy
.NET Framework 4.6.1 project did for years. `scripts/converted/` is ordinary (if
imperfect) game content like any other `.def`/`.scp` file under `scripts/` - this tool
is only run again deliberately, to recover specific missing/stale content from a fresh
Sphere source, not as part of any normal build/test/boot flow.

## I/O contract

`ConverterMain.Main()` (`SphereShardConverter/Main.cs`) takes no CLI arguments:

- **Input**: recursively scans `SphereShardConverter/convert/` for `.scp` files. This
  folder is gitignored - the third-party Erebor archive is never vendored into this
  repo. To populate it, clone the project's own GitHub fork (NOT the gitlab.com
  upstream - the user has made real modifications directly in the fork that upstream
  doesn't have, confirmed 2026-10-27):
  ```
  git clone --depth 1 https://github.com/pkorpel/erebor-sphere-archive.git SphereShardConverter/convert
  ```
- **Output**: writes converted files into `scripts/converted` by default - **the real,
  tracked content directory the live engine loads**. `ConvertedFile.Flush()` uses
  unconditional `FileMode.Create` with no skip-if-exists/merge logic anywhere in the call
  chain, so a careless run would silently overwrite every file it produces output for,
  including the files that carry hand-fix comments referencing issues like #157/#536/#539.

**Always redirect output away from `scripts/converted` for any exploratory or trial run**
via the `MORIA_CONVERTER_OUTPUT_DIR` environment variable, which overrides the hardcoded
default:
```
MORIA_CONVERTER_OUTPUT_DIR=/path/to/scratch dotnet run --project SphereShardConverter
```
Only point this at the real `scripts/converted` intentionally, once a diff against the
scratch output has already been reviewed - see #544 for the trial-run/diff/report
workflow this safety rail exists for.

## Nothing defined twice (#937)

A boot logs no error at all, and `BootLogTests` keeps it so, for a new world and a saved one. The engine treats a
second definition as an error and drops it, so the converter settles every double before writing:

- **The engine's own scripts win.** `HandWrittenScripts` scans `scripts/` except `converted` before converting. A
  constant or a thing they already define is commented out. Their values can differ on purpose: `attr_` and `statf_`
  flags are other bits here.
- **A model number used twice.** Sphere redoes the def and keeps both names on it. Here a later section with a name of
  its own stands as a def of that name, with the number as its model, so `c_orc` and `c_orc_nb` both exist. Without a
  name it only repeats the number: the first stays if it has a name, otherwise the later one counts.
- **A constant defined twice in the archive:** the later one counts, as in Sphere. Files are read in sorted order, so
  this doesn't depend on the file system.
- **A dupe's `DEFNAME`** is kept (`i_rock_3`, `i_pet_horse`). `DEFNAME2` isn't possible here, so a recipe naming one is
  written under the first name (`i_lemon` is `i_fruit_lemon`).

The rest of what's in the archive and can't load:

| What | Done with it |
|---|---|
| An item whose model is nowhere | Commented out (`i_dialog_context`), `i_coin_gold` is `i_gold` |
| A recipe naming an item that's nowhere | The line is commented out (`i_enchant_weapon`) |
| `ADDSPELL` of a spell that doesn't exist here | Commented out: `s_chain_lighting`, `s_meteor_shower`, `s_summon_undead`, `s_fire_bolt` |
| `TSPEECH` of a speech that's nowhere | Commented out |
| A constant with no value | An empty string, as in Sphere |
| `TEVENTS` on a `PlayerDef` | Dropped |
| An NPC's `RESOURCES` | Written as `amount name`, an empty one dropped |

`[MultiItemDef]` sections are live now, so deeds' names resolve. Their `COMPONENT` and `MULTIREGION` lines are still
comments, so such a multi has no doors or sign, and Erebor's deeds still don't place them.

## Recipes of hand-written items (#962)

Erebor's live recipes (`nastaveni_cm_resources_*`, `nastaveni_cm_skillmake_*` in `save/sphereworld.scp`) override the `.scp` files. `ConvertedItemDef.ApplyLiveRecipe` writes them into every converted item. Items written by hand never pass through it, and the archive has no `[ITEMDEF]` for spell scrolls at all, so `ConvertedRecipes` writes those into `scripts/converted/systems/craftmenu/craftrecipes.def` as `[CraftRecipeDef]`s, which `CraftRecipeDef` applies to the item at boot. It's a generated file: change a recipe in the archive, not there.

## Live skill values (#962)

`nastaveni_skilldelay_*`, `nastaveni_skilleffect_*` and `nastaveni_skilladvrate_*` in `save/sphereworld.scp` override spheretables.scp, as recipes do. `ConvertedSkillValues` writes them to `scripts/converted/systems/skillvalues.def`, and `SkillValuesDef` applies them at boot, over what the hand-written skill sections say. So to know a skill's real numbers, read that file, not spheretables.
