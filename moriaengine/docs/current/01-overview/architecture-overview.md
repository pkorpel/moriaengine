# Architecture overview

moriaengine is a .NET 8 port of SteamEngine, a C# Ultima Online server emulator built on
the Sphere scripting model. This page is the 30,000-foot view; deeper detail lives in the
pages linked from each section.

## The two real server processes

A running shard is **two separate OS processes**, each with its own listening port
(configured in `steamengine.ini`/`steamaux.ini`):

- **AuxiliaryServer** (`AuxiliaryServer/`) - the login server. Listens on port `2593` for
  real UO client connections (the classic "login server" protocol: account/password,
  server list, pick-a-shard) and on `2594` for RemoteConsole connections. It does not run
  any gameplay - its only job for a game client is to authenticate and then redirect the
  client to a GameCore instance.
- **GameCore** (`GameCore/`) - the actual game world. Listens on port `2595`
  (`[ports] game` in `steamengine.ini`) for the client connection AuxiliaryServer redirected.
  Everything gameplay-related - world state, scripts, items, characters, combat, the
  database of saved content - lives in this one process.

A real client's connection sequence is therefore: connect to AuxiliaryServer:2593 → log in
→ receive a server list → pick one → get redirected (new TCP connection) to that server's
GameCore:2595 → character list → enter the world. The test harness
(`Tests/Protocol/TestLoginClient.cs` / `TestGameClient.cs`) exercises this exact two-hop
flow for every protocol test that needs a real character in the world. See
[Networking & the protocol layer](../02-engine-core/networking-protocol.md) for the packet
level detail.

There's also a third, optional tool, **RemoteConsole** (`RemoteConsole/`) - a GUI client for
the remote-console protocol on port 2594. It targets `net8.0-windows` (WinForms) and is in
`SteamEngine.sln` since #29, so it compiles in every build, Linux and CI included, but it
only runs on Windows.

## Top-level projects and what they're for

| Project | Role |
|---|---|
| `GameCore` | The engine itself: world model, networking, LScript interpreter, region/timer/persistence infrastructure, and the script-compilation pipeline described below. |
| `Common` | Shared utility code with no engine-specific dependencies (logging, misc helpers) used by both GameCore and AuxiliaryServer. |
| `Communication` | The low-level TCP connection/packet-framing layer shared by both server processes. |
| `scripts` (`SteamEngine.CompiledScripts` project) | All game *content and gameplay logic* - not compiled into GameCore's own assembly ahead of time, but compiled fresh by GameCore at every boot (see below). This is where essentially all of the actual gameplay systems documented under [Gameplay systems](../README.md#4-gameplay-systems) live. |
| `Generated` | Not source - the output of the central code-generation pipeline (see [Scripting & code generation pipeline](../02-engine-core/scripting-pipeline.md)). Checked out of source control entirely; regenerated by running GameCore. |
| `Tests` | The xUnit test suite. Two tiers: fast unit-style tests at the top level, and `Tests/Protocol/` - full end-to-end tests that boot real `AuxiliaryServer`/`GameCore` child processes and drive them with a real wire-protocol client. See [Test infrastructure](../07-testing/test-infrastructure.md). |
| `AuxiliaryServer` | The login-server process described above. |
| `ProcessRestarter` | A small watchdog/supervisor utility for keeping a server process running. |
| `SphereShardConverter` | A one-time offline tool that migrated the original Erebor shard's real Sphere content into moriaengine's own `.def`/`.scp` format (the `scripts/converted/` tree is its output). Not part of the running server. |
| `RemoteConsole` | The GUI remote-console client described above. |
| `ThirdParty` | Vendored third-party dependencies. |
| `Languages` | Per-language localization override files (see [Localization](../05-localization.md)). |

## The Sphere-style content model, in brief

Game content - item types, NPC types, spells, skills, regions, houses, and so on - is
authored as text, not hand-written C# classes, following the Sphere-style
`[ThingTemplate X : Y]` convention:

```
[ItemDef 0x9999]
DEFNAME = i_attr_flag_test
NAME = Attr Flag Test Item
ATTR = attr_static|attr_magic
```

Three different file extensions are used by convention for different *kinds* of content,
though they all ultimately go through the same LScript loader:

- **`.ct`** - class *templates*, one per C# gameplay class (e.g.
  `scripts/Basic/ItemClasses/Item.ct` sits next to `Item.cs`). These declare the typed
  fields a class needs and drive C# code generation - see
  [Scripting & code generation pipeline](../02-engine-core/scripting-pipeline.md).
- **`.def`** - *definitions*: the actual `[ItemDef ...]`/`[CharacterDef ...]`/etc blocks
  that create real, loadable content (an item type, an NPC type, a house type...).
- **`.scp`** - everything else written in raw LScript: dialogs, trigger groups, standalone
  functions, and content that doesn't fit the `.def` block-per-template shape.

At boot, every `.def`/`.scp` file under `scripts/` is parsed and the content it describes
becomes available by its `DEFNAME` (e.g. `i_attr_flag_test`), ready to be instantiated into
a real in-world `Item`/`Character`/etc via `ThingDef.Create(...)`. See
[The Thing model](../02-engine-core/thing-model.md) for how a `.def` block turns into a
live object.

## Boot sequence

This is the part that surprises people coming from a normal compiled-ahead-of-time .NET
project: **GameCore recompiles `scripts/` from source on every single boot**, it does not
simply load a prebuilt `SteamEngine.CompiledScripts.dll`. The relevant code is
`GameCore/CompiledScripts/CompilerInvoker.cs`'s `CompileScripts` method, which does, in
order:

1. Invokes MSBuild against `scripts/SteamEngine.Scripts.csproj` (`CompilerInvoker.
   CompileScriptsUsingMsBuild`, logged as "Compiling scripts...") - a fresh, real compile
   of every `.cs` file under `scripts/`, every time.
2. Registers the resulting assembly's classes (`ClassManager.InitClasses`).
3. Runs the **central** code generator (`GeneratedCodeUtil.WriteOutAndCompile`), which
   writes a handful of files directly into the repo-root `Generated/` folder - one per
   registered generator (compiled `SteamFunction`/command dispatch tables, trigger-group
   tables, save/deep-copy implementors, and the reflection metadata backing the generic
   `.info` dialog). These are logged individually ("Generating compiled ScriptHolders",
   "Generating compiled Triggergroups", etc).
4. Compiles *that* generated code and loads it too.

Separately, **`ClassTemplateParser`** processes every `.ct` file and writes a
*per-class* `X.Generated.cs` file co-located next to the `.ct`/`.cs` it came from (e.g.
`Item.Generated.cs` next to `Item.ct`/`Item.cs`) - a different generation mechanism from
step 3 above, even though both ultimately produce files with the same `*.Generated.cs`
naming convention. Neither kind of generated file is checked into source control; both
need regenerating (by running GameCore, typically twice in a row - once to produce the
first generation, once more because the first run's own new types need to exist before the
second pass's reflection-based generators can see them) whenever a `.ct` file changes or a
new `[SteamFunction]`/trigger-dispatched class is added. `build.ps1` automates this
(`Invoke-ScriptGeneration`); see
[Scripting & code generation pipeline](../02-engine-core/scripting-pipeline.md) for the
full mechanics and the manual regeneration steps when `pwsh` isn't available.

Once script compilation and code generation succeed, GameCore loads the actual game world
(regions, accounts, saved items/characters from the most recent `saves/<date>/<time>/`
snapshot) and starts listening for connections.
